## 기존 콘셉트 이미지에서 바로잡은 부분
- 이미지의 '3~4개월'은 산정 근거가 없으므로 일정 약속으로 사용하지 않습니다. 단계별 완료 조건을 기준으로 진행합니다.
- 기술 버전은 이미지에서 복사하지 않습니다. 공식 문서를 확인한 뒤 호환되는 안정 버전을 lockfile로 고정합니다.
- Better Auth와 Supabase Auth를 동시에 도입하지 않습니다. 이 안은 Supabase Auth를 선택합니다.
- Colyseus와 Supabase Realtime으로 같은 게임 상태를 이중 전파하지 않습니다. 게임 동기화는 Colyseus입니다.
- AG Grid, S3/SeaweedFS, Redis, 별도 작업 큐, Three.js는 첫 버전의 필수 요소가 아닙니다.
- 이미지의 게임명·인원·점수·카드 묶음은 설명용 시각 자료입니다. 실제 동작은 텍스트 명세를 따릅니다.
- 사진의 목표 확장은 첫 구현에서 제외합니다. 사진에 목표 카드가 보여도 기본 덱에 넣지 않습니다.

## 기술 결정 ADR
### ADR-01: DOM 기반 게임 화면
카드 수가 적은 턴제부터 시작하고 웹 접근성·반응형·폼·로그와 같은 UI를 한 코드베이스로 유지합니다. 실제 3D 카메라가 제품 핵심이 아니므로 Three.js/Godot/Unity를 기본 도구로 삼지 않습니다. 렌더링 교체는 규칙 모듈과 독립적으로 가능하게 합니다.
### ADR-02: 서버 권위형
클라이언트는 행동 의도만 전송합니다. 손패·덱·차례·규칙·점수·난수는 서버가 검증합니다. 방장도 게임 상태의 신뢰 주체가 아닙니다.
### ADR-03: 모임과 게임 분리
Table은 멤버·초대·대화를 보관하고, GameSession은 한 판의 상태를 보관합니다. 게임을 바꾸어도 Table은 유지하고 sessionId를 새로 발급합니다.
### ADR-04: 단일 서버부터
첫 배포는 Node.js 게임 서버 1개와 PostgreSQL입니다. 다중 인스턴스·Redis·자동 수평 확장은 운영 지표를 확인한 뒤 도입합니다.
### ADR-05: 코드와 데이터의 판본 고정
`rulesVersion`, `contentVersion`, `schemaVersion`, `protocolVersion`을 구분합니다. 진행 중인 게임은 새 규칙으로 자동 변환하지 않습니다.

## 아직 결정하지 않은 것
도메인, 최종 서비스명, 실제 아트 스타일 확정, 운영자 계정, OAuth 공급자, 호스팅 업체·요금제, 뒤의 네 게임 상세 규칙/카드 데이터, 계정 삭제·로그 보관 최종 정책입니다. 개발 AI가 이를 사실로 꾸며내면 안 됩니다.
